# Второе ядро (Xray) и совместимость REALITY — архитектурная проработка

Статус: черновик к обсуждению. Версия приложения на момент написания: 0.2.1 (26).

## 1. Зачем

Провайдеры всё чаще поднимают серверы на Xray-core. 24.10 мы упёрлись в конкретный
случай: сервер `147.45.213.169:25567` (VLESS + REALITY, `flow=xtls-rprx-vision`,
`sni=kookas.fi`) **работает в INCY и не работает в FreedomCat**.

Проверено локально одним и тем же конфигом:

| клиент | результат |
|---|---|
| sing-box 1.12.19-neko-1 (наше ядро) | `reality verification failed` |
| sing-box 1.14.4 (upstream, свежий) | `reality verification failed` |
| Xray-core 26.10.21 (движок INCY) | соединение устанавливается |

Контроль: другой сервер той же подписки (`46.8.158.237:23214`) с теми же ключами и
SNI в sing-box подключается. Значит дело не в разборе подписки и не в версии ядра,
а в несовместимости REALITY-клиента sing-box с этим конкретным сервером Xray.

Отсюда два пути: добавить Xray как второе ядро либо довести наш sing-box до
совместимости с Xray-серверами.

## 2. Как устроено сейчас

```
VpnService (Kotlin)                       ← TUN, per-app split tunneling (allowed/disallowed)
  └─ Libcore.openTun(...)                 ← fd уходит в Go (BoxPlatformInterface)
       └─ libcore.BoxInstance.Start()     ← sing-box стартует с готовым JSON
            └─ sing-box (tun, dns, route, outbounds)
ConfigBuilder (Kotlin)                    ← профиль → sing-box JSON (route.final = TAG_PROXY)
BoxInstance / ProxyInstance (Kotlin)      ← жизненный цикл, статистика, логи, выбор outbound
```

Точки интеграции, которые придётся трогать:

| файл | роль |
|---|---|
| `app/.../bg/VpnService.kt` | создание TUN, fd → `openTun`, per-app списки |
| `app/.../bg/proto/BoxInstance.kt` | сборка конфига и запуск ядра |
| `app/.../fmt/ConfigBuilder.kt` | генерация sing-box JSON, `route.final`, правила |
| `app/.../fmt/v2ray/V2RayFmt.kt` | сборка outbound для VLESS/VMess/Trojan (база для трансляции) |
| `libcore/box.go` | `Start/Close/QueryStats/SelectOutbound` — контракт ядра |

Важно: per-app сплит-туннель живёт в `VpnService` (`addAllowedApplication` /
`addDisallowedApplication`), а не в ядре, поэтому он переживает смену ядра без правок.

## 3. Вариант C — починить REALITY в нашем sing-box (сначала исследование)

Идея: понять, чем ClientHello sing-box отличается от Xray, и поправить REALITY-клиент
в форке `sstpnk/sing-box`.

**Причина найдена (25.10):** sing-box **сам вырезает** пост-квантовый key share
X25519MLKEM768 из своего ClientHello, а REALITY-сервер Xray 26.x такой хендшейк
**отвергает**:

- deps/sing-box/common/tls/reality_client.go — два фильтра, которые убирают
  X25519MLKEM768 из SupportedCurvesExtension и KeyShareExtension;
- xtls/reality/tls.go (сервер) — после разбора key share стоит
  if peerPub2 == nil { break } с комментарием «reject outdated/strange Client Hello
  that doesn't have X25519MLKEM768 before optional X25519».

Проверено снятием ClientHello: Xray-клиент шлёт X25519MLKEM768 (1216 байт), sing-box
(и наш форк, и upstream 1.14.4) — только x25519. На серверах со старым Xray это
работает, на новых — нет.

Первая попытка патча (убрать фильтры) не помогла: сервер берёт X25519-ключ **из
гибридного** share (последние 32 байта), а sing-box считает общий секрет по отдельному
x25519 share (HandshakeState.State13.KeyShareKeys.Ecdhe) — ключи не совпадают.
Значит нужно и оставить гибридный share, и брать ECDH-ключ из него, как это делает
Xray-клиент.

**Оценка:** исследование сделано; правка — 0,5–1 день, если metacubex/utls отдаёт
X25519-ключ гибридного share. Если не отдаёт — переезд форка на

efraction-networking/utls (как у Xray), это уже 3–5 дней. Риск: правка живёт в форке
ядра и требует переноса при каждом обновлении sing-box.

**Плюсы:** одно ядро, без роста APK, без второго набора конфигов.
**Минусы:** результат не гарантирован; поддержка форка.

## 4. Вариант B — Xray как «транспорт» под sing-box (рекомендуемый компромисс)

Идея: не заменять ядро, а использовать Xray только для установки соединения с сервером.

```
VpnService → sing-box (tun, dns, route, split-tunnel, статистика)
                 └─ outbound socks 127.0.0.1:PORT
                        └─ Xray (socks inbound → vless/reality) → сервер
```

Что это даёт:

- TUN, DNS, fakeip, правила маршрутизации, per-app, статистика — остаются на sing-box,
  ничего не транслируем и не теряем;
- REALITY/транспорты делает Xray, то есть сервер видит «правильного» клиента;
- «ядро» в настройках превращается в «транспорт»: `sing-box` (как сейчас) или
  `sing-box + Xray`, с авто-переключением при ошибке REALITY.

Что нужно сделать:

1. **Сборка Xray.** Взять `AndroidLibXrayLite` (официальные gomobile-биндинги Xray,
   на них работает v2rayNG), собрать `libxray.aar` тем же способом, что `libcore.aar`
   (gomobile + NDK), добавить в CI рядом с libcore.
2. **Транслятор профиля → Xray outbound.** Только outbound, без TUN/DNS/route:
   `vless`, `vmess`, `trojan`, `shadowsocks`, `socks`, `http`, `wireguard` (без
   AmneziaWG), транспорты `tcp/ws/grpc/httpupgrade/xhttp`, TLS/REALITY/uTLS.
   Основа — существующий `V2RayFmt.buildSingBoxOutbound*`, маппинг один-в-один.
3. **Жизненный цикл.** `XrayTransport` (Kotlin): выбор свободного порта, запуск/стоп
   вместе с сервисом, ожидание готовности socks (health-check), перезапуск при смене
   профиля, корректная остановка в `:bg`-процессе.
4. **Интеграция в конфиг.** В `ConfigBuilder` при `transport = Xray` вместо реального
   outbound подставляется `{"type":"socks","server":"127.0.0.1","server_port":PORT}`,
   тег остаётся `proxy` → все правила и селектор работают без изменений.
5. **Настройки.** `Движок: Авто / sing-box / Xray-транспорт` + переопределение на
   профиле. «Авто» = пробуем sing-box, при `reality verification failed` перезапускаем
   через Xray и запоминаем выбор для этого профиля.
6. **Статистика и логи.** Трафик считает sing-box на socks-outbound (работает как
   есть). Логи Xray — отдельный буфер, писать в тот же файл с префиксом.

**Оценка:** 5–8 дней, включая сборку AAR и тесты. **Рост APK:** +5–7 МБ на ABI
(Xray .so ~15–20 МБ в распакованном виде).

**Риски:** два бинарника в APK; лишний локальный хоп (по задержке незаметно);
лицензия Xray — MPL-2.0 (совместима с GPL-3.0, добавить в `AUTHORS`).

## 5. Вариант A — полноценное второе ядро Xray

Xray забирает всё: TUN, DNS, маршрутизацию, статистику.

```
VpnService (TUN, per-app) → tun2socks (hev-socks5-tunnel) → Xray socks → outbounds
```

Что дополнительно нужно против варианта B:

1. **tun2socks.** `libhev-socks5-tunnel` (JNI) — так делает INCY и v2rayNG.
   Нужен свой конфиг, свои маршруты/DNS, обработка IPv6, MTU.
2. **Трансляция DNS и правил.** `dns` (remote/direct/fakeip), `route.rules`
   (домены, ip_cidr, порты, geoip/geosite), `final` → Xray `dns` + `routing`.
   Полного соответствия нет: fakeip — только sing-box; geo-ресурсы у Xray свои
   (`geosite.dat`/`geoip.dat`, другой формат).
3. **Статистика и выбор outbound.** Через gRPC Stats API Xray (отдельная работа,
   сейчас у нас `QueryStats`/`SelectOutbound` из libcore).
4. **Совместимость профилей.** AmneziaWG, TUIC, Hysteria, AnyTLS — только sing-box:
   при выборе Xray такие профили придётся блокировать с понятным сообщением.

**Оценка:** 3–5 недель. **Плюсы:** полная совместимость с Xray-серверами «из коробки»,
не нужен sing-box для трафика. **Минусы:** два полноценных стека, двойная площадь
багов, потеря части протоколов, больше кода и тестов.

## 6. Сравнение

| | C: починить sing-box | B: Xray как транспорт | A: второе ядро целиком |
|---|---|---|---|
| Срок | 2–3 дня + правка (3 дня–2 нед) | 5–8 дней | 3–5 недель |
| Рост APK | 0 | +5–7 МБ/ABI | +8–10 МБ/ABI |
| Риск | средний (форк ядра) | низкий | высокий |
| Что теряем | ничего | ничего | AmneziaWG/TUIC/Hysteria в режиме Xray, fakeip |
| Совместимость с Xray-серверами | если гипотеза верна — полная | полная для поддерживаемых протоколов | полная |
| Поддержка в будущем | правки при каждом апдейте sing-box | два апстрима | два апстрима + tun2socks |

## 7. Рекомендация

1. **Сначала C — исследование (2–3 дня).** Если окажется, что дело в key share или
   session_id, это может быть патч на несколько десятков строк, и вопрос закрывается
   без второго ядра и без роста APK.
2. **Если C не даёт быстрого результата — делаем B.** Это 80% пользы A за 20% работы:
   REALITY и транспорты уходят в Xray, всё остальное (TUN, DNS, маршруты, per-app,
   статистика) остаётся проверенным sing-box.
3. **A — только если появится требование «Xray единственное ядро»** (например,
   провайдер требует Xray-специфичные фичи, которых нет в sing-box).

## 8. Поэтапный план (если идём по рекомендации)

**Этап C1 — диагностика (2–3 дня).**
Локальный Xray-сервер, дамп ClientHello от Xray и sing-box, отчёт с разницей.
Критерий: назван конкретный параметр, из-за которого сервер отвергает sing-box.

**Этап C2 — патч (если применимо, до 1–2 недель).**
Правка в `deps/sing-box`, тест на локальном сервере и на сервере провайдера.
Критерий: `147.45.213.169:25567` подключается из FreedomCat.

**Этап B1 — сборка Xray AAR (1–2 дня).**
`libxray.aar` в CI рядом с `libcore.aar`, кэш по коммиту.
Критерий: приложение собирается с двумя AAR, размер APK измерен.

**Этап B2 — транспорт (2–3 дня).**
`XrayTransport` + транслятор outbound для vless/vmess/trojan/ss + socks-обвязка в конфиге.
Критерий: профиль с REALITY подключается через Xray, трафик считается.

**Этап B3 — выбор и авто-фолбэк (2 дня).**
Настройка «Движок», переопределение на профиле, авто-переключение при ошибке REALITY,
сообщения в UI.
Критерий: пользователь видит, каким движком идёт соединение, и может выбрать вручную.
